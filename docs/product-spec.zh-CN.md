# LiteView 图片查看器产品与技术方案

> 评估基线：当前工作区仅包含本文档，尚无代码、构建清单、测试资产或 Git 历史。本文中的性能和工期均为待验证的工程目标，不是实测结论。

## 0. 评审结论

**结论：有条件通过，建议缩减首版范围后进入技术验证。**

LiteView 的核心方向可行：Rust、egui 与 wgpu 可以支撑跨平台桌面 UI、非阻塞解码和 GPU 瓦片渲染；本地优先、无账号、无后台建库的定位也具有清晰差异。但原方案把多格式支持、精确广色域、亿级像素、批量文件操作和 AI 同时放入首版，范围过大，风险不可控。

建议首版聚焦 Windows 10/11 x64 的单图查看、目录浏览、相邻图片切换、基础 EXIF、SDR 色彩管理和 JPEG 大图瓦片渲染。JPEG、PNG、WebP 为必选格式；AVIF、HEIC、JXL、RAW、HDR、批量写操作、本地 AI 和后端索引均放到后续版本。完整多格式、HDR 与 RAW 不应作为 v1 承诺。

## 1. 产品定位与成功标准

### 1.1 目标用户

- 需要频繁查看本地照片或素材的摄影爱好者、办公用户和小型创作团队。
- 主要操作是双击打开、前后翻页、快速放大检查细节，并偶尔按目录浏览。
- 用户重视启动速度、显示正确、界面克制、不上传文件。

### 1.2 核心用户旅程

1. 从文件管理器双击图片，应用在 1 秒内显示可辨认画面。
2. 使用方向键连续翻页，已预加载的相邻图片切换无明显停顿。
3. 放大亿级像素 JPEG 检查局部时，UI 保持响应且显存占用有上限。
4. 打开当前目录，以缩略图网格定位图片，并查看基础 EXIF。
5. 遇到损坏或不支持的图片时看到明确原因，应用不崩溃。

### 1.3 产品原则

- **快**：先显示低分辨率预览，再补齐细节；所有慢操作离开 UI 线程。
- **准**：优先正确处理嵌入 ICC、EXIF 方向和像素纵横比；不支持的颜色能力必须明确降级。
- **安静**：默认离线，不弹广告，不后台建库，不自动修改原文件。
- **安全**：把图片和目录内容视为不可信输入；写操作必须显式确认并可恢复。

## 2. 范围与优先级

P0 是可进入集成验证的技术 MVP；P1 是对外发布的 v1；P2 是发布后的扩展。v1 必须同时满足 P0 与 P1。

| ID | 优先级 | 要求 | 验收要点 |
|---|---|---|---|
| F-01 | P0 | 打开图片 | 支持文件选择、命令行路径、拖放和 Windows“打开方式”；无效路径给出可恢复提示 |
| F-02 | P0 | 基础解码 | 必选静态 JPEG、PNG、WebP；正确处理 1 至 8 类 EXIF 方向、透明通道和灰度图 |
| F-03 | P0 | 查看操作 | 适应窗口、100%、滚轮缩放、拖拽平移和仅显示层面的 90° 旋转；不修改原文件 |
| F-04 | P0 | 相邻切换 | 当前目录内自然排序；预加载前后各一张低分辨率预览；切换可取消旧任务 |
| F-05 | P0 | 色彩管理 | 将嵌入 ICC 转换到 sRGB 输出；缺失配置按 sRGB 处理；异常配置降级并提示 |
| F-06 | P0 | 大图保护 | 先显示预览，再按可见区域加载瓦片；108MP JPEG 不整图上传 GPU，不因尺寸直接崩溃 |
| F-07 | P1 | 目录网格 | 仅扫描当前目录、不递归；缩略图按需生成、限制并发、滚动时取消不可见任务 |
| F-08 | P1 | 全屏与键盘 | 全屏、缩放、翻页和返回操作均有快捷键；控件可获得焦点并显示工具提示 |
| F-09 | P1 | 基础元数据 | 显示尺寸、文件大小、拍摄时间、相机和镜头等常用 EXIF；解析失败不影响看图 |
| F-10 | P1 | 错误与设置 | 覆盖损坏文件、无权限、文件被删除和超限文件；记住窗口、缩放模式和缓存上限 |
| F-11 | P1 | 平台集成 | Windows 文件关联、任务栏图标、单实例或明确的打开策略；安装包可卸载 |

### 2.1 后续范围

- **P2 管理能力**：批量重命名、格式转换、按 EXIF 过滤。写操作必须单独设计预览、冲突规则、失败恢复和临时文件清理。
- **P2 格式扩展**：AVIF、HEIC/HEIF、JPEG XL、RAW。按实际用户需求和依赖许可逐项评估。
- **P2 显示扩展**：显示器 ICC、广色域和 HDR。该能力需要自定义 GPU 表面与输出管线，不能只靠普通 sRGB 纹理实现。
- **P2 智能能力**：本地语义搜索、缩略图索引和可选 AI 模型，默认关闭且不得进入基础启动路径。

### 2.2 明确不做

- 云同步、账号体系、在线分享、遥测广告或任何默认网络请求。
- 完整 DAM、持久化资产数据库、递归索引整个磁盘。
- 修图、图层、批处理工作流、视频、OCR、文档扫描和移动端首发。
- 未经用户确认的覆盖、移动、删除或格式转换。

## 3. 格式支持策略

格式不能只按扩展名判断；应优先读取文件签名，再结合扩展名选择解码器。

| 格式 | 版本 | 要求与技术备注 |
|---|---|---|
| JPEG | P0 | 必选；支持基线、渐进式、灰度和 CMYK；优先使用缩放或条带解码以满足大图要求 |
| PNG | P0 | 必选；支持透明、16 位源和隔行扫描；超大文件限制 CPU 内存并保留预览降级路径 |
| WebP | P0 | 仅静态图片；支持透明和动画容器的静态首帧处理；动画播放放到 P2 |
| AVIF | P1 条件项 | 仅在依赖、许可、内存和性能通过技术验证后进入 v1，否则明确提示不支持 |
| HEIC/HEIF | P2 | 不得依赖系统可选插件；跨平台解码和专利/分发许可需单独评审 |
| JPEG XL | P2 | 比较 jxl-oxide 与 libjxl 的性能、体积和维护成本后决定 |
| RAW | P2 | 仅承诺经过验证的相机型号列表；需要解码、去马赛克和色彩配置，工作量远高于普通格式 |

- 所有解码器必须设置像素数、单图内存、总并发和时间预算，防止构造文件导致资源耗尽。
- 损坏、截断、伪装扩展名和缺失 ICC 的文件必须返回结构化错误，而不是 panic。
- JPEG 大图是 P0 的硬指标；其他格式可先显示降采样预览。若不能流式随机访问，只有通过临时瓦片缓存或明确降级后才能宣称完整支持。

## 4. 交互与界面要求

- **单图模式**：画面占据主要空间，工具栏保持克制；加载、缩放比例和错误状态不能遮挡主要内容。
- **目录模式**：缩略图网格显示文件名和当前选中态；大目录分批加载，滚动离开视口时取消任务。
- **缩放基准**：“适应窗口”和“100%”必须稳定；缩放以鼠标位置为中心，平移不改变缩放级别。
- **旋转语义**：查看旋转只影响显示，不写回 EXIF 或像素；如后续提供“保存旋转”，必须作为独立写操作确认。
- **默认快捷键**：左右方向键切换，加减号缩放，0 适应窗口，1 显示 100%，F 全屏，R 旋转查看，Esc 退出全屏或关闭浮层。

## 5. 技术架构

```text
系统入口 / 文件选择 / 拖放 / 文件关联
                    |
             app：UI、命令与状态机
              /                  \
    egui/wgpu 渲染线程       有界解码线程池
       |                         |
   瓦片缓存与上传调度 <----- 解码 -> ICC -> 缩放/LOD
       |                         |
   帧输出                     文件、EXIF、目录快照
                    |
         可选 ai（独立 feature，默认关闭）
```

### 5.1 目标模块

```text
src/main.rs          # 进程入口和平台初始化
src/app/             # UI、命令、会话状态、快捷键
src/image/           # 格式探测、解码、LOD 与瓦片请求
src/color/           # ICC 解析、转换和色彩测试接口
src/render/          # egui/wgpu 纹理、缓存、绘制策略
src/metadata/        # EXIF 与基础文件信息
src/files/           # 目录快照、自然排序、路径与文件操作
src/platform/        # 文件关联、单实例和系统集成
src/config/          # 本地配置与迁移
src/ai/              # 后续能力，单独 feature
tests/               # 集成、回归与性能测试
assets/fixtures/     # 可再分发的小型测试图片
```

### 5.2 核心数据与状态

- `ImageDescriptor`：规范化路径、文件标识、尺寸、格式、EXIF 方向、ICC 哈希、透明通道和像素纵横比。
- `TileKey`：图片会话代数、缩放层级、瓦片坐标和颜色处理版本，避免旧任务写入新会话。
- `ImageSession`：`Idle -> Opening -> PreviewReady -> Interactive -> Closing`，失败时进入 `Error` 并保留可重试信息。
- `ResourceBudget`：统一约束解码线程、CPU 中间缓冲、瓦片显存和预加载，而不是分散设置缓存上限。

### 5.3 并发规则

- UI 线程不执行同步文件枚举、全图解码或耗时的 ICC 转换。
- 解码池默认使用 `min(CPU 物理核数 - 1, 4)` 个线程；请求队列有界，可见瓦片优先于相邻图片预加载，预加载优先于目录缩略图。
- 切换图片或缩放级别时递增会话代数；旧请求即使完成也只能被丢弃，不能污染当前画面。
- GPU 上传由渲染线程分批完成，每帧设置上传上限，避免一次补齐大量瓦片造成卡顿。

## 6. 关键技术设计

### 6.1 解码与降采样

- 元数据探测先行：读取尺寸、方向、ICC 存在性和解码上限，再决定是否允许解码。
- 首屏优先使用最快路径生成不超过 4096 像素长边的预览；缩放时再按可见区域请求高阶瓦片。
- JPEG 优先使用缩放解码或条带解码；PNG/WebP 使用流式或增量解码。依赖库必须通过真实大图验证，不能假设所有格式都能随机访问局部。
- 缩放使用统一的边界规则和滤波策略，避免瓦片拼接接缝；后台解码结果保持不可变，缓存通过键引用而不是原地修改。

### 6.2 色彩管理

- v1 仅承诺 SDR。解码结果统一转换为 sRGB 8 位 RGBA 后上传，透明像素使用预乘 alpha。
- 有嵌入 ICC 时执行一次配置文件到 sRGB 的转换；无配置按 sRGB 解释；损坏或不可处理配置降级并显示非阻塞警告。
- 不对已是 sRGB 的数据重复应用转换，避免双重 gamma。颜色转换结果必须缓存，缩放和重复绘制不能重复做昂贵计算。
- 使用公开 ICC 测试图和固定参考输出验证颜色误差，目标为平均 ΔE2000 ≤ 2、最大 ≤ 3；超限必须记录原因。
- 显示器 ICC、广色域和 HDR（PQ/HLG）不属于 v1。它们需要独立的 GPU 表面、色彩空间协商和平台测试矩阵。

### 6.3 瓦片、缓存与大图

- 默认瓦片大小为 512×512，层级按 1/1、1/2、1/4 递减；具体尺寸在技术验证中结合设备纹理上限调整。
- 显存预算默认 256 MiB，预览图、可见瓦片和预取瓦片共用预算；可见瓦片固定，其余按 LRU 淘汰。
- 瓦片缺失时先放大显示已有预览，禁止留下空白或阻塞等待；缩放和窗口尺寸变化触发新请求。
- 目标测试样本包括 20MP JPEG 和 12000×9000（约 108MP）JPEG；后者必须可预览、可局部放大、可关闭，且显存不随源像素量线性增长。
- 目录扫描和缩略图仅限当前目录。v1 不建立持久数据库；如需临时索引，必须位于可清理的缓存目录并支持完整删除。

### 6.4 相邻图片预加载

- 按自然数字排序构造当前目录快照；文件数量变化时重新扫描，不递归进入子目录。
- 只预加载前后各一张，默认使用不超过 2048 像素长边的预览；缓存不足或后台繁忙时允许跳过。
- 用户快速连续翻页时只保留最新方向的请求，避免旧预加载占满队列。

### 6.5 文件操作边界

- v1 的查看、旋转和元数据显示均为只读；应用不得在打开图片时写入源目录。
- P2 的批量重命名和转换必须先生成变更预览，明确同名冲突、失败回滚和原文件保留策略。转换默认写新文件，不覆盖输入文件。
- 临时文件使用随机名称和用户权限，异常退出后在下次启动清理；不跟随目录符号链接进行递归扫描。

### 6.6 可选 AI 边界

- AI 不进入 v1，不参与启动、看图、翻页或基础搜索。
- 启用后仍默认本地推理，不发送图片或元数据；模型下载必须由用户主动触发并校验哈希。
- 模型、向量索引和缩略图缓存均可单独删除；关闭或删除失败不得影响基础查看器。

## 7. 非功能要求

### 7.1 基准环境

除非另注，性能指标均在 release 构建、Windows 11、4 核 8 线程 CPU、16 GB 内存、集成显卡、SATA SSD、系统缓存已预热的条件下采集，报告 p95 而不只报告最好成绩。技术验证后应记录实际设备型号。

| 指标 | 目标 | 验证方式 |
|---|---|---|
| 冷启动到可交互 | ≤ 500 ms | 连续启动 30 次记录 p95 |
| 20MP JPEG 适应窗口 | ≤ 250 ms | 固定测试图，从打开命令到首帧 |
| 已预加载相邻切换 | ≤ 50 ms | 连续翻页并记录画面更新时间 |
| 未命中的相邻预览 | ≤ 300 ms | 清除缓存后测量首次可见 |
| 缩放/平移帧率 | ≥ 55 FPS | 4K 窗口连续操作 10 秒 |
| 108MP JPEG 首预览 | ≤ 1.5 s | 固定大图样本和基准设备 |
| 查看器显存占用 | ≤ 256 MiB | 大图缩放稳定后读取 GPU 指标 |
| 空闲内存 | ≤ 200 MB | 打开单图后静置 60 秒 |
| 连续翻页 200 张 | 内存无持续增长 | 前后对比 RSS，允许 10% 波动 |
| 核心安装包 | ≤ 40 MB | 不含后装模型和未启用编解码器 |
| 默认网络请求 | 0 | 网络监控和代码审计 |

### 7.2 兼容与可用性

- MVP 以 Windows 10/11 x64 为主；macOS 13+ 和 Ubuntu 22.04 LTS 在 v1 后逐平台验证，不根据“Rust 跨平台”直接视为已完成。
- 正确处理 UTF-8 文件名、中文路径、长路径、只读文件和文件在查看期间被移动或删除。
- UI 在 100% 至 200% 系统缩放下布局不重叠；所有图标提供工具提示，关键操作可仅用键盘完成。

## 8. 可靠性、安全与隐私

- 图片解码是最主要的外部输入边界。所有解码器必须有尺寸上限、超时/取消机制和错误隔离；FFI 解码器需要在发布前做依赖审计和模糊测试。
- 默认完全离线；不收集文件路径、图片内容、设备信息或使用行为。日志不得记录完整敏感路径，除非用户主动导出诊断信息。
- 不自动执行图片附带的脚本或外部资源，不调用 shell 打开未知文件。
- 批量写操作属于高风险能力，必须经过单独安全评审；v1 保持只读可显著降低数据损坏风险。
- 任何缓存、配置和模型文件都应位于标准用户目录，记录可删除位置，并在卸载时提供清理选项。

## 9. 测试与质量门槛

- **单元测试**：自然排序、格式探测、错误映射、缓存淘汰、会话代数、颜色配置读取和无损缩放边界。
- **集成测试**：JPEG/PNG/WebP 的打开、方向、透明、损坏文件、目录变化、前后切换和设置恢复。
- **渲染回归**：使用固定 ICC 图和缩略样本比较输出；GPU 测试允许小幅平台差异，但必须保存差异图。
- **模糊测试**：对文件探测、EXIF、ICC 和至少一个通过 FFI 接入的解码器进行离线 fuzz。
- **性能测试**：将 20MP、108MP、极宽图、极长图和 16 位 PNG 纳入固定基准集，防止优化回退。
- 纯逻辑模块目标行覆盖率 ≥ 80%；GPU、平台集成和 FFI 路径优先用集成、回归和人工验收补齐，不能只用覆盖率代替实际测试。
- CI 至少执行 Windows 构建；macOS/Linux 后续加入编译矩阵。提交前执行：

```sh
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-targets
cargo build --release
```

## 10. 实施路线与工作量评估

| 阶段 | 交付物 | 通过条件 | 粗略工作量 |
|---|---|---|---|
| 0. 技术验证 | eframe/egui/wgpu 样机、20MP 与 108MP JPEG、ICC 测试图、性能日志 | 首预览、显存和交互达到目标的 1.5 倍以内；明确瓦片方案 | 1–2 人周 |
| 1. P0 看图核心 | 打开、解码、缩放、方向、前后切换、瓦片缓存和错误状态 | P0 功能通过，无 UI 阻塞和可复现崩溃 | 3–5 人周 |
| 2. P1 目录与集成 | 当前目录网格、预加载、EXIF、全屏、设置和 Windows 文件关联 | 大目录可取消、内存有界、安装卸载通过 | 3–5 人周 |
| 3. 发布加固 | 测试样本、性能基准、安装包、崩溃处理和发布文档 | 第 12 节全部满足，已知风险有记录 | 2–3 人周 |

合计约为 **9–15 人周**，适用于一名熟悉 Rust 和桌面图形开发的工程师；若由单人兼职推进，实际日历周期通常更长。以下工作不计入上述估算：

- macOS/Linux 兼容与打包：约 4–8 人周，取决于平台文件关联和 GPU 差异。
- 每新增一种 AVIF/JXL/HEIC 解码：约 1–3 人周，HEIC 的许可与平台差异可能更高。
- RAW 支持：至少 4–8 人周，且需要持续维护相机兼容性。
- 本地 AI 搜索：约 4–8 人周，包含模型管理、索引、性能和隐私测试。

## 11. 项目评估与决策建议

### 11.1 可行性判断

| 能力 | 可行性 | 复杂度 | 主要风险 | 建议 |
|---|---|---|---|---|
| 单图查看与目录浏览 | 高 | 中 | 跨平台 UI 与输入细节 | 作为 v1 核心 |
| SDR ICC 到 sRGB | 高 | 中 | 错误配置、双重 gamma、瓦片接缝 | v1 必须自动化验证 |
| 108MP JPEG 瓦片查看 | 中 | 高 | 解码器随机访问、缓存调度和 GPU 上限 | 技术验证后再锁定 |
| PNG/WebP 超大图细节 | 中 | 高 | 流式解码与局部访问不统一 | 允许先预览，必要时临时缓存 |
| 全部格式兼容 | 中低 | 高 | 许可、平台差异、维护成本和攻击面 | 分版本引入 |
| 批量重命名与转换 | 中 | 高 | 数据损坏、冲突、回滚 | 移出 v1 |
| 广色域与 HDR | 中低 | 高 | egui 表面能力、系统色彩协商 | 单独立项 |
| 本地 AI 语义搜索 | 中 | 高 | 模型体积、推理性能、索引生命周期 | 保持可选和隔离 |

### 11.2 总体判断

- 架构方向合理，但当前文档不能作为“全功能首版”的承诺。核心技术风险集中在大图解码随机访问、ICC 正确性、GPU 资源上限和跨平台编解码器。
- 建议以 Windows x64、JPEG/PNG/WebP、SDR 色彩、只读查看作为 v1 的硬边界；先用技术验证决定是否继续采用 egui 默认纹理管线或增加自定义 wgpu 渲染层。
- 如果 108MP 场景在技术验证中连续两次触发 OOM，或首预览超过目标 1.5 倍，应暂停扩展功能，优先更换瓦片/解码方案；不要用降低验收标准掩盖架构问题。
- 当前工作区没有实现和实测数据，因此本评估是方案级判断。只有在阶段 0 产出基准报告后，才能给出可靠的发布日期和性能承诺。

### 11.3 建议锁定的产品决策

1. v1 只承诺 Windows 10/11 x64，跨平台进入后续路线。
2. v1 必须支持 JPEG、PNG、WebP；AVIF 需单独通过依赖与性能门槛。
3. v1 不包含批量写操作、HDR、RAW 和 AI，避免安全与性能风险叠加。
4. 保留格式适配器、元数据源和本地语义索引接口，但不在 v1 实现未验证能力。

## 12. 发布定义

满足以下条件才可标记 v1 完成：

- F-01 至 F-11 全部通过验收，且没有未记录的关键缺陷。
- 20MP/108MP JPEG、损坏文件、透明图片、ICC 样本和大目录回归通过。
- 性能目标在基准设备上完成实测；未达标项必须有书面豁免和后续计划。
- 默认离线、只读源文件、无凭据和无遥测行为通过检查。
- `cargo fmt`、`cargo clippy`、`cargo test` 和 release 构建通过。
- 第三方编解码器、字体和测试图片的许可证已核对，安装、升级和卸载可用。
- 用户文档说明支持格式、已知限制、快捷键、缓存位置和错误恢复方式。

开发命令、提交规范和仓库约定见 [AGENTS.md](AGENTS.md)。
